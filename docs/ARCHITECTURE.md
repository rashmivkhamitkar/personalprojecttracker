## 1. Architecture Overview

The application is a **single ASP.NET Core Razor Pages web app** targeting **.NET 10**. The server builds complete HTML pages and stores data in a **SQLite** database file using **Entity Framework Core (EF Core)**.

| Layer | Technology | Why it was chosen |
|---|---|---|
| User interface | Razor Pages + HTML/CSS (Bootstrap 5 from the project template) | One page per screen, with forms, model binding, and validation messages built in. No JavaScript framework to learn. |
| Data access | EF Core | Lets you write C# classes and LINQ instead of SQL. Migrations keep the database in step with your classes. |
| Storage (development) | SQLite | A single database file with no server to install. Data survives restarts, which satisfies PRD F8. |
| Testing | xUnit test project | Covers the rules that are easy to get wrong: the deadline views and progress. |

**Alternatives considered and rejected for this MVP:**
- **MVC:** needs more files per screen.
- **Blazor:** adds render modes and live connections.
- **SPA + Web API:** means building two applications.
- **Dapper:** means writing SQL and mapping code by hand.
- **SQL Server or PostgreSQL:** need a database server.

Each would work, but each costs time that a 45-minute-per-day schedule cannot spare.

### Request and data flow

```
 ┌─────────┐  1. GET /Projects or POST form    ┌──────────────────────────┐
 │ Browser │ ────────────────────────────────▶ │ Razor Page (PageModel)   │
 │ desktop │                                   │  - binds form input      │
 │ /mobile │                                   │  - validates (ModelState)│
 └─────────┘                                   └────────────┬─────────────┘
      ▲                                                     │ 2. LINQ query / SaveChanges
      │                                                     ▼
      │                                        ┌──────────────────────────┐
      │                                        │ TaskViewService          │ (deadline views + progress)
      │                                        │ AppDbContext (EF Core)   │
      │                                        └────────────┬─────────────┘
      │                                                     │ 3. SQL
      │                                                     ▼
      │                                        ┌──────────────────────────┐
      │  5. HTML response                      │ SQLite file: app.db      │
      └─────────────────────────────────────── │                          │
            (4. .cshtml view renders data)     └──────────────────────────┘
```

**Post/Redirect/Get:** After a successful form submission, the page **redirects** to another page instead of returning HTML directly. That way, refreshing the browser does not submit the form a second time.

## 3. Main Components and Responsibilities

| Component | Responsibility | Should **not** do |
|---|---|---|
| `Program.cs` | Registers services (`AppDbContext`, `TaskViewService`, `TimeProvider`) and configures middleware (HTTPS, error page, routing). | Contain business logic. |
| `Models/Project`, `Models/TaskItem` | Describe the data and its validation rules (attributes such as `[Required]`). | Talk to the database. |
| `AppDbContext` | Maps models to tables and configures the relationship and cascade delete. | Contain page logic. |
| Page models (`*.cshtml.cs`) | Handle one screen: load data on GET, validate and save on POST, then redirect. Simple CRUD uses `AppDbContext` directly. | Duplicate the date or progress rules. |
| Views (`*.cshtml`) | Render HTML from page-model data. | Query the database. |
| `TaskViewService` | The **only** place that decides what "today", "overdue", and "progress" mean. | Render HTML. |
| `TimeProvider` (built into .NET) | Supplies the current time. Tests can replace it with a fake clock. | — |

**Why not route all CRUD through services?** For create, read, update, and delete, a service would only pass calls through to EF Core. Logic goes into a service only when it has real rules (the deadline views and progress) or is needed in more than one place.

## 4. Initial Data Model

### Decisions (confirmed 2026-10-21)

| PRD question | Options considered | Decision | Reason |
|---|---|---|---|
| Q5: Must a task belong to a project? | Required / optional | **Required** | Simpler model; every task counts toward a project's progress. Trade-off: the user must create a project before adding tasks. |
| Q6: How many projects per task? | One / many | **Exactly one** (one-to-many) | Many-to-many would make progress harder to reason about and is not needed. |
| Q7: Deleting a project that has tasks | Cascade / block | **Cascade after confirmation** | One action, and no tasks left without a project. The Delete page tells the user how many tasks will also be deleted. |
| How to store completion status | `bool` / completion timestamp | **`bool IsCompleted`** | The PRD only needs complete or incomplete. A timestamp would be a new feature. |

### Entities

```
┌──────────────────────┐ 1        * ┌──────────────────────────┐
│ Project              │────────────│ TaskItem                 │
├──────────────────────┤            ├──────────────────────────┤
│ Id         int  PK   │            │ Id          int     PK   │
│ Name       string    │            │ Title       string       │
│            required  │            │             required     │
│            max 100   │            │             max 200      │
│ Tasks      list      │            │ DueDate     DateOnly?    │  ← optional calendar date
└──────────────────────┘            │ IsCompleted bool         │  ← default false
                                    │ ProjectId   int     FK   │  ← required
                                    │ Project     nav. prop.   │
                                    └──────────────────────────┘
```

- **Why `TaskItem` and not `Task`?** .NET already has `System.Threading.Tasks.Task`, which is used in every `async` method. Reusing the name would cause confusing compiler errors. The database table can still be named `Tasks`.
- **Progress is calculated, not stored.** Storing a `Progress` column would mean updating it on every task change, and it could fall out of sync. Calculating it on demand is always correct.
- **Answers to the remaining PRD questions** (confirmed 2026-10-26):

| PRD question | Decision | Reason |
|---|---|---|
| Q11: Maximum lengths | Name: 100 characters. Title: 200 characters. | Prevents unbounded input. Long enough for normal names and titles. |
| Q12: Unique project names | Not enforced. | The PRD does not require it, and enforcing it adds a validation case. |
| Q13: Past due dates | Allowed. | Users must be able to record tasks that are already late, and you need them to test Overdue. |
| Q8: Confirm task delete | Yes, using a Delete confirmation page. | Matches project delete; the page is generated by scaffolding. |

## 5. Persistence with EF Core and SQLite

1. `AppDbContext` has two tables: `DbSet<Project> Projects` and `DbSet<TaskItem> Tasks`.
2. `Program.cs` registers it with `AddDbContext<AppDbContext>(o => o.UseSqlite(...))`. The connection string `Data Source=app.db` lives in `appsettings.json`.
3. **Migrations** are C# files that describe schema changes. They are created with `dotnet ef migrations add <Name>` and applied with `dotnet ef database update`. Migration files are committed to Git; the `app.db` file is **not**, because it holds your personal data.
4. **Cascade delete** is configured explicitly in `OnModelCreating`, even though it is EF Core's default for a required relationship. Writing it out documents the decision. EF Core turns on SQLite's foreign-key enforcement automatically.
5. **Dates in SQLite:** SQLite has no date type. EF Core stores `DateOnly` as text in the form `yyyy-MM-dd` (for example, `2026-10-21`). Text in this form sorts and compares in true date order, so `<`, `=`, and `>` comparisons are correct in SQL.
6. **Why this meets F8:** every change is written to `app.db` by `SaveChangesAsync()` before the page redirects. Closing and reopening the app reads the same file.

**Limitations to remember:**
- SQLite allows only one writer at a time. That is fine for one user.
- Some cloud hosts reset their disks, which would delete `app.db`. The production database is therefore an **open decision** (Section 8).

## 6. Validation and Error Handling

| Situation | How it is handled | User sees |
|---|---|---|
| Empty or whitespace-only name or title | `[Required]` on the property. Its default setting already treats whitespace-only strings as empty. | A message next to the field, e.g. "Project name is required." |
| Value too long | `[StringLength(100)]` or `[StringLength(200)]` | A message next to the field |
| Leading or trailing spaces | The page model trims the value before saving | Nothing; the value is saved clean |
| Task's project does not exist (tampered form) | The page model checks that the project exists before saving and adds a `ModelState` error | A message on the form |
| Item not found (deleted, or a bad URL) | Return `NotFound()` | A 404 page |
| Save fails (`DbUpdateException`) | `try/catch` around `SaveChangesAsync()`. The error is logged, a page-level `ModelState` error is added, and the form is shown again **with the user's input kept**. | "Your changes could not be saved. Please try again." |
| Any unexpected error | `UseExceptionHandler("/Error")` outside development; the detailed developer page during development | A friendly error page |

- **The server is the authority.** The template's client-side validation scripts give instant feedback, but every rule is checked again on the server, because browser checks can be bypassed.
- **Rule of thumb for page models:** on POST, `if (!ModelState.IsValid) return Page();`. Otherwise, save and then redirect.

## 7. How Today, Upcoming, and Overdue Get Their Data

All three views call `TaskViewService`, which works like this:

```
today = DateOnly.FromDateTime(timeProvider.GetLocalNow().DateTime)

Today:    !IsCompleted && DueDate == today      order by Title
Upcoming: !IsCompleted && DueDate >  today      order by DueDate, then Title
Overdue:  !IsCompleted && DueDate <  today      order by DueDate (oldest first), then Title
```

Each query runs **in the database**, translated to SQL by EF Core, and includes the task's project name for display.

**Calendar-date implications:**
- **No time of day.** Because `DueDate` is a `DateOnly`, a task due today is "Today" all day long, and there are no midnight edge cases inside the comparison itself.
- **`null` drops out automatically.** Tasks without a due date have `DueDate = null`. In both C# and SQL, any comparison with `null` is false, so these tasks never appear in the three views. That is exactly what the PRD requires. Tests will confirm it.
- **Each task appears in at most one view.** For any date, exactly one of `<`, `==`, and `>` is true.
- **"Today" comes from the server's clock (confirmed decision).** Running locally, the server's clock is your PC's clock, so "today" is correct. If the app is later hosted on a server in another time zone (often UTC), "today" could be wrong for part of each day. Because "today" comes only from the injected `TimeProvider`, fixing this later changes one line, not every page. This is tracked in Section 8.
- **Tests use a fake clock.** `FakeTimeProvider` from the `Microsoft.Extensions.TimeProvider.Testing` package lets tests set "today" to any date, such as 2026-10-19 to match the PRD's example table.

**Progress (F7):** calculated per project as `total == 0 ? 0 : completed * 100 / total`. Integer division rounds **down**, so 199 of 200 shows 99%, never a misleading 100%. A project with no tasks shows 0%, as the PRD requires.

**Testing approach:** the tests run `TaskViewService` against an **in-memory SQLite** database (`Data Source=:memory:`). That way they check the real SQL translation of the date comparisons, not just C# logic.

## 8. Open Decisions: Security, Authentication, and Deployment

These are **not decided**. Decide them before the app is used anywhere except your own computer.

| # | Open question | Why it matters | When to decide |
|---|---|---|---|
| D1 | **Authentication:** none, a single password, or user accounts (ASP.NET Core Identity)? | Without sign-in, anyone who can reach the app can see and change all data. That is safe on `localhost`, but **not** on the public internet. D1 and D2 must be decided together. | Before any deployment |
| D2 | **Hosting:** local only, or a cloud host? | This decides the production database, the time zone, and the HTTPS setup. | After the MVP works locally (around Day 28) |
| D3 | **Production database:** keep SQLite on persistent storage, or move to a server database? | Some hosts erase local files. EF Core makes a later switch fairly cheap, because only the provider and migrations change. | With D2 |
| D4 | **Time zone for "today"** when hosted | See Section 7. | With D2 |
| D5 | **Backups** of `app.db` | Your data lives in one file. | With D2 |

**Protections that come built in** with this stack, at no extra cost:
- **Cross-site request forgery:** Razor Pages forms include anti-forgery tokens automatically.
- **Cross-site scripting:** Razor HTML-encodes output by default.
- **SQL injection:** EF Core sends values as parameters.
- **HTTPS:** the template turns on HTTPS redirection.

**One rule to follow:** any action that changes data (create, edit, delete, toggle complete) uses **POST**, never a GET link.
